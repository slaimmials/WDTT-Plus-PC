# Ручная установка сервера WDTT Plus

`server-installer/install.sh` устанавливает `wdtt-server` на VPS из
Linux-терминала. Это альтернатива установке из приложения WDTT Plus для тех,
кто не хочет передавать программе SSH-доступ к серверу.

Комплект содержит `wdtt-server` версии `20` и автономный установщик `0.20.3`,
совместимый с контрактом деплоя `1`. Версия скрипта ведётся отдельно от версии
сервера. Используйте файлы из одного выпуска.

```bash
bash server-installer/install.sh --version
bash server-installer/install.sh compatibility
```

После установки подключайтесь из WDTT Plus: понадобятся публичный адрес VPS,
DTLS-порт, главный пароль туннеля и действующий VK-хеш.

## Что нужно подготовить

Для установки нужен совместимый комплект:

- `install.sh`;
- исполняемый бинарник `wdtt-server` версии `20` для Linux `amd64`
  (`x86_64`);
- `SHA256SUMS` для проверки скрипта и бинарника.

Установщик поддерживает только VPS с Linux `amd64` и `systemd`.

Установщик специально не скачивает код из интернета и не поддерживает
`curl | sh`: оператор сам передаёт на VPS проверенные файлы.

### Скачать готовый комплект

На странице выпуска WDTT Plus в разделе **Assets** публикуются:

```text
WDTT-Plus-server-v20-installer-0.20.3-linux-amd64.tar.gz
WDTT-Plus-server-v20-installer-0.20.3-linux-amd64.tar.gz.sha256
```

Первый файл — готовый серверный комплект для Linux `amd64`, второй — его
контрольная сумма. Скачайте оба файла из одного выпуска и сначала проверьте
архив:

```bash
sha256sum -c WDTT-Plus-server-v20-installer-0.20.3-linux-amd64.tar.gz.sha256
tar -xzf WDTT-Plus-server-v20-installer-0.20.3-linux-amd64.tar.gz
cd WDTT-Plus-server-v20-installer-0.20.3-linux-amd64
```

После распаковки внутри находятся три согласованных файла:

```text
install.sh
wdtt-server
SHA256SUMS
```

Это статический Linux `amd64`-файл `wdtt-server` версии `20`; внешние
динамические библиотеки ему не нужны. Проверьте внутренние файлы и их версии:

```bash
sha256sum -c SHA256SUMS
bash install.sh --version
./wdtt-server --version
```

Проверка должна сообщить `install.sh: OK`, `wdtt-server: OK`, версию
установщика `0.20.3` и версию сервера `20`.

Готовые бинарник и контрольные суммы публикуются как файлы конкретного
выпуска, но не хранятся в истории Git. Так пользователь получает проверенный
комплект, согласованный с исходным кодом именно этой версии.

Не используйте бинарники из посторонних источников и не смешивайте
`install.sh` с сервером из другой версии проекта.

### Как собрать самостоятельно

Сервер собирается из каталога `server/` репозитория:

```bash
cd server
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 \
  go build -buildvcs=false -trimpath -ldflags="-s -w" \
  -o ../server-installer/wdtt-server .
cd ..
chmod 0755 server-installer/wdtt-server
(cd server-installer && sha256sum install.sh wdtt-server > SHA256SUMS)
server-installer/wdtt-server --version
```

Готовый архив выпуска собирается командой
`server-installer/release_bundle.sh` (результат — в `dist/`). Go нужен только
на машине сборки, на VPS он не требуется.

## Какой сценарий выбрать

| Состояние VPS | Правильное действие |
| --- | --- |
| WDTT Plus ещё не установлен | Запустить мастер из раздела «Быстрый старт» |
| Сервер уже принадлежит ручному установщику | Выполнить сохраняющее обновление через `install` |
| Сервер установлен вкладкой **Деплой** | Продолжить управлять им из приложения либо явно выполнить `adopt-android` |
| Сервер удалён в приложении с сохранением данных | Восстановить его из **Деплой** либо явно выполнить `adopt-android` с новым бинарником |
| Ручную установку нужно вернуть вкладке **Деплой** | Проверить план и явно выполнить `handoff-android` |
| Найдены неполные, чужие или изменённые вручную файлы WDTT | Ничего не перезаписывать; выполнить `doctor` и выяснить происхождение файлов |

Обычная команда `install` никогда автоматически не забирает управление у
деплоя из приложения и не перезаписывает неизвестную установку.

## Быстрый старт

Это самый короткий путь для нового пустого VPS с готовым проверенным
комплектом `install.sh`, `wdtt-server` и `SHA256SUMS`.

Под «пустым» понимается VPS без существующих `/etc/wdtt`, `wdtt.service`,
`/usr/local/bin/wdtt-server`, интерфейса `wdtt0` и конфликтующего маршрута
`10.66.66.0/24`. Мастер проверяет это сам и при неоднозначности останавливается
до изменений.

### 1. Передайте скрипт и бинарник на VPS

```bash
scp server-installer/install.sh \
  server-installer/wdtt-server \
  server-installer/SHA256SUMS \
  root@your-vps:/tmp/
```

На VPS ещё раз проверьте бинарник перед запуском мастера:

```bash
cd /tmp
sha256sum -c SHA256SUMS
./wdtt-server --version
```

### 2. Запустите главное меню

На VPS:

```bash
sudo bash /tmp/install.sh
```

В главном меню переходы выполняются одной клавишей без Enter. Ввод путей,
паролей и подтверждений остаётся обычным текстовым вводом.

Для чистой установки выберите:

```text
Установка и обновление → Мастер установки или обновления
```

Мастер:

- проверит совместимость с деплоем из приложения;
- создаст защищённый начальный `passwords.json`;
- предложит ввести главный пароль вручную или сгенерировать безопасный;
- проверит VPS, бинарник, порты, WireGuard, маршруты и межсетевой экран;
- покажет план;
- изменит сервер только после точного подтверждения словом `УСТАНОВИТЬ`.

Если хотите открыть мастер сразу без входа в меню:

```bash
sudo bash /tmp/install.sh wizard --binary /tmp/wdtt-server
```

### 3. Проверьте результат и подключите клиент

После сообщения об успешной установке выполните:

```bash
sudo bash /tmp/install.sh doctor
sudo bash /tmp/install.sh monitor
```

Проверьте также, что выбранный DTLS UDP-порт разрешён не только на самом VPS,
но и в сетевом экране или группе безопасности панели VPS-провайдера. Скрипт не
может менять правила в панели провайдера.

Затем вручную добавьте сервер в WDTT Plus. Установка на VPS сама по
себе не создаёт профиль на телефоне, не получает VK-хеш и не передаёт главный
пароль приложению.

## Быстрое обновление уже установленного сервера

Возьмите новый готовый `server-installer/wdtt-server` из совместимого
комплекта либо соберите его самостоятельно по инструкции выше. Передайте
бинарник вместе с актуальным `install.sh` и `SHA256SUMS` на VPS,
повторно проверьте контрольную сумму и выполните:

```bash
sudo bash /tmp/install.sh install --binary /tmp/wdtt-server
```

Для сервера, которым уже владеет ручной установщик, `--config` при
обновлении не нужен. Скрипт возьмёт текущие порты, DNS и лимиты из установленной
конфигурации, сохранит весь `/etc/wdtt`, проверит запуск и откатит изменения
при ошибке.

Если версия скрипта, хеш бинарника, файл службы, настройки и состояние службы
уже совпадают, повторный запуск завершится без резервной копии, замены файлов
и перезапуска.

## Если сервер уже установлен из приложения WDTT Plus

Ручной установщик не захватывает деплой из приложения или оставленные им данные
автоматически.

Если запустить мастер на таком сервере, он безопасно остановится без изменений
и предложит выбор:

1. оставить управление сервером из вкладки **Деплой** в WDTT Plus;
2. явно принять совместимый деплой из приложения или сохранённые им данные под ручной
   установщик.

Для явного перехода:

```bash
sudo bash /tmp/install.sh check --binary /tmp/wdtt-server
sudo bash /tmp/install.sh adopt-android --binary /tmp/wdtt-server
```

`adopt-android` принимает только один из двух однозначных вариантов:

- работающий деплой из приложения с совместимой меткой контракта;
- состояние после команды приложения **Удалить сервер, сохранить данные**: unit и
  бинарник отсутствуют, а защищённые `passwords.json`, `wg-keys.dat` и точная
  метка сохранения находятся в `/etc/wdtt`.

Перед изменением команда резервирует всё существующее состояние и весь
`/etc/wdtt`. Затем она устанавливает переданный `wdtt-server`, создаёт файл
службы ручной установки и сохраняет данные `/etc/wdtt`, включая клиентов,
пароли, привязки устройств, историю и настройки. Если приложение уже удалило
службу и бинарник, откат восстанавливает именно это состояние без службы и
бинарника. Показывается точный план и требуется подтверждение `УСТАНОВИТЬ`.

Если деплой из приложения старый и ещё не содержит метку совместимости, сначала
откройте WDTT Plus на телефоне и выполните **Обновить с сохранением**. Новый
деплой добавит метку без удаления базы и WireGuard-ключей. После этого можно
запускать `adopt-android`.

Поддельная метка, symlink, небезопасные права, лишний unit или бинарник,
некорректная база и неизвестные либо вручную изменённые установки отклоняются
без изменений.

Передача управления через `adopt-android` не отключает Android как VPN-клиент.
Она меняет владельца серверной установки: после успешного перехода основным
безопасным путём установки и обновления становится только ручной установщик.
приложение WDTT Plus распознаёт нового владельца и не запускает поверх него свой
деплой.

## Как вернуть ручную установку под управление приложения

Обратный переход выполняет отдельная команда `handoff-android`. Она доступна
только для установки, которой уже безопасно владеет этот ручной установщик.
Чужой, неполный или уже управляемый приложением сервер команда не изменяет.

Сначала покажите план без изменений:

```bash
sudo bash /tmp/install.sh handoff-android --dry-run
```

Затем выполните передачу:

```bash
sudo bash /tmp/install.sh handoff-android
```

То же действие доступно в главном меню: **«Установка и обновление» →
«Передать ручную установку обратно деплою из приложения»**. Перед изменением скрипт
показывает точный план и требует слово `ПЕРЕДАТЬ`. Для контролируемой
автоматизации разрешён `--yes`; другие параметры установки команда не
принимает.

Передача выполняется как транзакция:

- проверяется работоспособность текущей ручной службы;
- сохраняются бинарник, unit, метка владельца, сетевой helper, состояние
  межсетевого экрана и весь `/etc/wdtt`;
- создаётся совместимый unit с маркер приложенияом и версией контракта;
- служба запускается и проходит проверку с теми же портами и лимитами;
- при любой ошибке возвращаются ручной unit, данные, состояние службы и
  собственное правило межсетевого экрана;
- после успеха удаляются только служебные unit-helper и ownership-файл
  standalone; его точное правило UFW/firewalld и защищённая метка сохраняются,
  чтобы текущий DTLS-порт не потерял внешнюю доступность.

`passwords.json`, WireGuard-ключи, клиенты, привязки устройств, история,
настройки и пользовательские резервные копии не изменяются. Бинарник также не
заменяется. Если служба до перехода была одновременно отключена и остановлена,
после обязательной временной проверки это состояние сохраняется.

После успешной передачи WDTT Plus распознаёт сервер как свой совместимый
деплой. Во вкладке **Деплой** можно выполнить **«Обновить с сохранением»**:
приложение загрузит актуальный серверный бинарник обычным путём приложения, не
сбрасывая базу и WireGuard-ключи. Сам `handoff-android` не запускает Android-
скрипт, не встраивает его в standalone и не передаёт приложению SSH-пароль.

деплой из приложения не меняет правила панели VPS-провайдера. Если после передачи в
приложении будет выбран другой DTLS-порт, разрешите новый UDP-порт в UFW,
firewalld и панели провайдера, затем отдельно удалите ненужное старое правило.
При неизменном порте сохранённое правило продолжает работать.

При необходимости сервер можно снова передать ручному установщику командой
`adopt-android`. Сохранённые пользовательские резервные копии не мешают обоим
направлениям перехода.

## Связь со вкладкой «Деплой»

деплой из приложения и ручной установщик используют одни и те же серверные сущности:

- `/usr/local/bin/wdtt-server`;
- `/etc/systemd/system/wdtt.service`;
- `/etc/wdtt/passwords.json`;
- `/etc/wdtt/wg-keys.dat`;
- сокет управления сервером;
- интерфейс `wdtt0`.

После ручной установки в приложении WDTT Plus остаются рабочими:

- обычное подключение к VPN;
- «Подключиться (без установки)»;
- импорт сервера;
- управление резервными копиями и их безопасное восстановление;
- клиентские профили;
- передача подключения файлом, QR-кодом и ссылкой;

Самостоятельно созданными клиентами можно также управлять прямо из главного
меню скрипта: показать безопасный список, создать клиента, вывести его данные
и ссылку `wdtt://`, активировать, приостановить, отвязать устройство или
удалить после отдельного строгого подтверждения. Главный пароль и пароли
выбранных клиентов передаются локальному серверу через стандартный ввод, а не
через аргументы процесса.

«Подключиться (без установки)» только использует введённые параметры готового
сервера и не меняет владельца установки. Профиль не появляется на телефоне
автоматически: адрес, DTLS-порт, главный пароль и VK-хеш нужно указать или
импортировать в приложении.

`install.sh` не входит в APK, не извлекается приложением и не запускается им на
VPS. Пока сервер принадлежит ручному установщику, он обновляется командой
`install` из этого каталога с новым локальным проверенным бинарником. Вернуть
право серверного деплоя приложению можно только отдельной транзакционной
командой `handoff-android`.

До выполнения `handoff-android` действия «Обновить с сохранением», повторный
деплой, «Начать с нуля» и удаление ручной установки из приложения намеренно
недоступны. Изменение портов в этот период также выполняется ручным
установщиком. После успешной передачи снова действует обычный деплой из приложения.

### Резервные копии после ручной установки

Совместимый `wdtt-server` v20 поддерживает тот же менеджер резервных копий и
после установки через этот скрипт. Управление находится в приложении WDTT Plus:
**«Деплой» → «Резервные копии и перенос»**. Для административных действий
нужны SSH-доступ к VPS и главный пароль WDTT; обычное VPN-подключение по-прежнему
не использует SSH.

Сервер может создавать копии по расписанию без запущенного приложения WDTT Plus,
показывает последнюю попытку и следующую дату, хранит заданное число исправных
снимков и не удаляет последнюю исправную копию. В снимок входят база WDTT,
WireGuard-ключи и сохранённый профиль выходного подключения. Копии пользователя
хранятся отдельно от краткоживущих транзакционных копий установщика, поэтому
обновление, откат и `adopt-android` их не стирают и не принимают за незавершённую
транзакцию.

Локальная копия на VPS доступна только root, но не спасает при потере самого
VPS. В приложении выбранный снимок можно проверить и скачать через системное
хранилище приложения; новый переносимый файл всегда шифруется отдельным паролем.
Его можно позднее выбрать на устройстве и восстановить. Перед восстановлением
приложение получает общую блокировку ручного установщика, создаёт постоянную
копию текущего состояния и готовит транзакционный откат. Сам `install.sh` для
этого в APK не нужен.

## Расширенный сценарий

Используйте этот путь, если нужно пройти установку по шагам, закрепить хеш
бинарника, подготовить автоматизацию или заранее проверить план.

### 1. Проверить совместимость

```bash
sudo bash /tmp/install.sh compatibility
```

Для автоматических проверок:

```bash
sudo bash /tmp/install.sh compatibility --machine
```

### 2. Создать начальную конфигурацию

```bash
sudo bash /tmp/install.sh init-config --output /root/wdtt-initial.json
```

В интерактивном режиме можно:

- ввести главный пароль вручную с повтором;
- сгенерировать безопасный уникальный пароль.

Сгенерированный пароль показывается только один раз. Сразу сохраните его в
менеджер паролей или другое защищённое место: этот пароль нужен владельцу для
подключения и управления сервером.

Генератор использует системный источник случайности и создаёт 32-символьный
стойкий пароль. Практическая вероятность совпадения с другим сгенерированным
паролем пренебрежимо мала. Для ручного пароля допустимо от 8 до 80 символов;
пробелы и символ `|` запрещены.

`init-config` создаёт обычный файл с правами `600` и никогда не перезаписывает
существующий файл.

Для автоматизации пароль можно передать не в аргументах, а первой строкой
отдельного закрытого файла:

```bash
sudo bash /tmp/install.sh init-config \
  --output /root/wdtt-initial.json \
  --password-file /secure/path/owner-password.txt \
  --yes
```

Файл пароля тоже должен иметь права `600`. Пароль, содержимое JSON, VK-хеши и
WireGuard-ключи в вывод не попадают.

### 3. Проверить план без изменений

```bash
sudo bash /tmp/install.sh check \
  --binary /tmp/wdtt-server \
  --config /root/wdtt-initial.json
```

`check` ничего не меняет на сервере. Он проверяет хост, бинарник, конфигурацию,
занятые порты, сетевые предпосылки и тип существующей установки.

### 4. Выполнить установку

```bash
sudo bash /tmp/install.sh install \
  --binary /tmp/wdtt-server \
  --config /root/wdtt-initial.json
```

Перед изменениями скрипт повторит проверки под `flock`, покажет точный план и
потребует слово `УСТАНОВИТЬ`.

После успешной установки `/root/wdtt-initial.json` можно удалить вручную, если
он больше не нужен как резервная копия. Рабочая база сервера находится в
`/etc/wdtt/passwords.json`.

### Неинтерактивный пример

```bash
sudo bash /tmp/install.sh install \
  --binary /tmp/wdtt-server \
  --config /root/wdtt-initial.json \
  --sha256 EXPECTED_SERVER_SHA256 \
  --dtls-port 56000 \
  --wg-port 56001 \
  --client-port 9000 \
  --dns 1.1.1.1 \
  --max-passwords 50 \
  --firewall none \
  --yes
```

`--yes` не означает «разрешить всё». Без явного `--firewall open` межсетевой
экран не меняется. Смена портов существующей установки требует отдельного
`--migrate-ports`. Используйте `--yes` только в контролируемой автоматизации:
он отключает обычное финальное подтверждение словом `УСТАНОВИТЬ`.

## Смена портов

Смена DTLS-, WireGuard- или локального порта у существующей установки разрывает
старые клиентские ссылки. В интерактивном режиме скрипт спрашивает отдельное
подтверждение с ответом по умолчанию «нет».

Для автоматического режима нужно явно указать:

```bash
sudo bash /tmp/install.sh install \
  --binary /tmp/wdtt-server \
  --dtls-port 56200 \
  --wg-port 56201 \
  --client-port 9200 \
  --migrate-ports \
  --yes
```

При этом транзакционно обновляются `default_ports`, профиль владельца и порты в
сохранённых клиентских ссылках. Уже импортированные профили на телефонах нельзя
изменить удалённо: после смены порта их нужно исправить или импортировать
заново.

Если старый входящий порт был открыт самим установщиком, его собственное
правило UFW/firewalld заменяется новым и входит в откат. Чужие правила и
правила без сохранённой метки не удаляются.

## Проверка, диагностика и мониторинг

Краткое состояние:

```bash
sudo bash /tmp/install.sh status
```

Подробная диагностика установленного сервера:

```bash
sudo bash /tmp/install.sh doctor
```

Безопасный мониторинг:

```bash
sudo bash /tmp/install.sh monitor
```

`status`, `doctor` и `monitor` не выполняют установку и не выводят секреты.
`status` даёт краткую сводку, `doctor` ищет причины неисправности уже
установленного сервера, а `monitor` показывает текущее состояние и агрегаты
работы. Для проверки нового бинарника и будущего плана до установки используйте
отдельную команду `check`.

`doctor` проверяет:

- тип установки и метку владельца;
- незавершённые транзакции;
- версию и запуск `wdtt-server`;
- защищённость `/etc/wdtt`;
- структуру `passwords.json`;
- наличие четырёх WireGuard-ключей;
- службу systemd, сокет управления, `wdtt0`;
- DTLS- и WireGuard-порты;
- IPv4 forwarding и NAT/FORWARD-правила WDTT;
- активный межсетевой экран.

`monitor` показывает службу, PID, CPU, память, время работы процесса, порты,
`wdtt0`, forwarding, DNS, лимит клиентов, агрегаты клиентов/устройств и общий
трафик за сегодня, 7 дней, 30 дней и всё время. Главный пароль, клиентские
пароли, VK-хеши и WireGuard-ключи скрыты.

Если у текущего пользователя нет прав на чтение `/etc/wdtt/passwords.json`,
запустите `monitor` через `sudo`.

## Требования к VPS

Поддерживаемый целевой сервер:

- Linux `amd64`;
- `systemd`;
- рабочий IPv4-маршрут по умолчанию и внешний сетевой интерфейс;
- свободная внутренняя подсеть `10.66.66.0/24`;
- `bash`;
- `jq`;
- `iproute2`;
- `util-linux` с `flock`;
- GNU coreutils, включая `sha256sum`, `stat`, `install`, `base64`, `sort` и
  `sync`;
- стандартные утилиты `awk`, `sed`, `grep` и `find`;
- `sysctl`;
- `systemd-analyze`;
- `iptables` либо `nftables`;
- для WireGuard `kernel` — команда `wg`;
- для WireGuard `userspace` — доступный `/dev/net/tun`.

В режиме WireGuard `auto` должен быть доступен хотя бы один из вариантов:
kernel или userspace.

Установщик проверяет зависимости, но не устанавливает их. Недостающие пакеты
нужно поставить администратору средствами своего дистрибутива. Для сборки
серверного бинарника нужен Go 1.25 или новее только на машине сборки; на
целевом VPS он не требуется.

## Что именно меняет установщик

Постоянные пути, которыми может управлять установщик:

- `/usr/local/bin/wdtt-server`;
- `/etc/systemd/system/wdtt.service`;
- `/etc/wdtt`;
- `/var/lib/wdtt-server-installer`.

Установщик:

- работает только с локальным бинарником;
- не устанавливает и не обновляет системные пакеты;
- не меняет SSH;
- не трогает чужие службы, сертификаты, обратные прокси и пакетные репозитории;
- не принимает неизвестную установку за свою;
- перед изменениями повторяет проверки под блокировкой;
- делает закрытую резервную копию;
- ведёт закрытый журнал транзакции;
- откатывает бинарник, файл службы, сетевой скрипт, состояние межсетевого экрана,
  метку владения и весь `/etc/wdtt` при ошибке.

Сам `wdtt-server` во время работы создаёт `wdtt0`, включает IPv4 forwarding,
меняет временные сетевые `sysctl` и добавляет NAT/FORWARD-правила. Установщик
показывает это до подтверждения и проверяет фактический результат после
запуска.

Входящий межсетевой экран меняется только после отдельного согласия и только
для одного активного UFW или firewalld. При прямом nftables/iptables или
неоднозначной конфигурации автоматическое изменение не выполняется: скрипт
показывает предупреждение, а правило нужно проверить вручную.

Установщик не создаёт VK-хеши и не управляет учётными записями VK. Он может
создать серверного клиента и подготовить совместимую ссылку подключения, но
сам импорт ссылки, QR-кода или файла и остальные настройки телефона
выполняются в WDTT Plus. Установщик также намеренно не содержит
команд удаления или сброса всех данных сервера.

## Защита от случайного подтверждения

В критических местах установщик не принимает одиночные латинские `y` и `n`.
Это защищает от ситуации, когда администратор видит русскую подсказку, но
клавиатура остаётся в латинской раскладке: физическая клавиша `Н` не станет
случайным `YES`.

В подтверждениях принимаются:

- `д` или `да`;
- `н` или `нет`;
- полные английские `yes` или `no`;
- пустой ответ, только если у вопроса явно показано значение по умолчанию в
  квадратных скобках.

В меню `Н · Назад` физическая латинская клавиша `Y` работает как возврат,
потому что это не разрушительное действие.

## Контракт совместимости

Канонический файл [compatibility-contract.env](compatibility-contract.env)
задаёт:

- версию контракта деплоя из приложения;
- совместимую версию `wdtt-server`;
- постоянные серверные пути;
- имена базы и WireGuard-ключей;
- маркеры деплоя из приложения, сохранённых данных приложения и ручной установки.

Проверка [compatibility_test.sh](tests/compatibility_test.sh) сверяет контракт,
`install.sh`, `client/internal/deploy/deploy.sh` и `server.go`. Отдельная проверка
[version_sync_test.sh](tests/version_sync_test.sh) сверяет номер выпуска у
приложения WDTT Plus, `wdtt-server` и верхней записи `CHANGELOG.md`, а также
целевую версию сервера в обоих установщиках, контракте и инструкции. Версия
самого скрипта остаётся отдельной. Если один путь изменён, а другой не обновлён,
Gradle-сборка останавливается до создания серверного бинарника и APK.

При изменении серверного протокола или цепочки деплоя из приложения обновляйте
одновременно:

1. `compatibility-contract.env`;
2. `install.sh`;
3. `client/internal/deploy/deploy.sh`;
4. тесты совместимости;
5. этот README.

## Справочник команд

```text
install.sh [menu] [--binary ПУТЬ] [--config ПУТЬ]
install.sh wizard [--binary ПУТЬ] [параметры]
install.sh init-config [--output ПУТЬ] [параметры]
install.sh check [параметры]
install.sh install [--binary ПУТЬ] [--config ПУТЬ] [параметры]
install.sh adopt-android [--binary ПУТЬ] [параметры]
install.sh handoff-android [--dry-run] [--yes]
install.sh status
install.sh monitor
install.sh doctor
install.sh compatibility
install.sh version | --version
```

Команды:

- `menu` — главное меню. Это действие по умолчанию.
- `wizard` — интерактивный мастер чистой установки или обновления.
- `init-config` — создать новый закрытый `passwords.json`.
- `check` — проверить VPS, бинарник, конфигурацию и план без изменений.
- `install` — выполнить первую установку или обновить свою ручную установку.
- `adopt-android` — явно принять совместимый деплой из приложения либо строго
  отмеченные сохранённые данные приложения под ручное управление.
- `handoff-android` — транзакционно вернуть собственную ручную установку под
  управление деплоя из приложения без изменения данных и ключей.
- `status` — кратко показать состояние без чтения секретов.
- `monitor` — показать безопасный мониторинг без секретов.
- `doctor` — выполнить расширенную диагностику без изменений.
- `compatibility` — показать контракт совместимости.
- `version` / `--version` — показать версию установщика.

Совместимые алиасы:

- `start` — то же самое, что `wizard`; оставлен для старых инструкций.
- `-V` — то же самое, что `--version`.

Основные параметры:

- `--binary ПУТЬ` — локальный бинарник `wdtt-server`.
- `--config ПУТЬ` — начальный закрытый `passwords.json`; нужен только при
  первой установке.
- `--output ПУТЬ` — новый файл для `init-config`.
- `--password-file ПУТЬ` — закрытый файл с главным паролем в первой строке.
- `--sha256 HEX` — ожидаемый SHA-256 локального бинарника.
- `--dtls-port ПОРТ` — публичный DTLS-порт, по умолчанию `56000`.
- `--wg-port ПОРТ` — внутренний WireGuard-порт, по умолчанию `56001`.
- `--client-port ПОРТ` — локальный локальный порт, по умолчанию `9000`.
- `--dns ЗНАЧЕНИЕ` — DNS для клиентов, по умолчанию `1.1.1.1`.
- `--max-passwords N` — начальный максимум клиентов, по умолчанию `50`.
- `--max-workers N` — лимит воркеров доступа, `0` означает без лимита.
- `--max-handshakes N` — одновременные рукопожатия.
- `--handshake-rate N` — рукопожатий в секунду.
- `--max-client-mbps N` — лимит Мбит/с доступа, `0` означает без лимита.
- `--wg-backend MODE` — `auto`, `kernel` или `userspace`.
- `--migrate-ports` — явно разрешить смену портов существующей установки.
- `--firewall MODE` — `ask`, `none` или `open`.
- `--advanced` — показать расширенные вопросы мастера.
- `--dry-run` — показать план без изменений.
- `--yes` — не задавать обычные вопросы и принять план установки.
- `--machine` — машинный вывод для `compatibility`.
- `-h`, `--help` — показать справку.

## Подключение клиента после ручной установки

В приложении WDTT Plus не используйте SSH-раздел для обычного VPN-подключения.
Для владельца сервера в профиле туннеля укажите:

- IP-адрес или домен VPS;
- выбранный DTLS-порт;
- главный пароль;
- действующий VK-хеш.

Главный пароль создаётся мастером и должен быть заранее сохранён
администратором. VK-хеш установщик не создаёт.

Для отдельного клиента откройте в главном меню **Управление клиентами → Создать
клиента**. Скрипт может попросить сервер сгенерировать уникальный пароль,
проверит введённый VK-хеш и после создания один раз покажет готовые поля и
ссылку `wdtt://connect`. Эту ссылку можно вставить в WDTT Plus. Списки и
мониторинг не раскрывают клиентские пароли; повторный вывод данных требует
ввода главного пароля и точного пароля выбранного клиента.

Файл и QR-код удобнее создавать уже в приложении WDTT Plus после импорта ссылки:
так используется единый формат WDTT Plus и не требуется устанавливать на VPS
генератор QR-кодов.

SSH нужен только для ручной установки, администрирования, обновления или
диагностики сервера; обычный VPN-трафик через SSH не проходит.
